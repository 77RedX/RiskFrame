# RiskFrame UI audit — 2026-11-11

## Scope and verification

Audited the Docker-served website at http://localhost:3000 with Microsoft Edge via Playwright. Examined desktop (1440, 1024), tablet (768), and mobile (390, 320) widths; stock search/selection; optimization; signals; portfolio deposits/trades; account forms; copilot rendering; keyboard access; and persistence behavior.

Account requests were intercepted using an isolated synthetic profile. No real account was created or edited, and no actual broker orders were placed. A live, read-only optimization request was used to verify the constraint mismatch. Browser interception scenarios deliberately injected failures or fixtures and are identified below.

P1 means fix before public deployment or AI-provider integration; P2 means functional/usability correction; P3 means polish. These findings are not a claim that all possible defects have been found.

## P1 — Copilot messages execute raw HTML

**Evidence:** browser-confirmed with an intercepted assistant reply. A harmless image error handler set a boolean marker on the isolated page; no data was read or sent. Both user and assistant messages go through the same renderer. This demonstrates script-capable HTML injection, not a demonstrated cross-account attack in the current app.

**Location:** `website/src/components/AgentCopilot/AgentCopilot.jsx:101`, `:167`.

`formatMarkdown` performs substitutions without escaping HTML, then `dangerouslySetInnerHTML` inserts the result. Connecting an AI provider would introduce another source of untrusted text into this path.

**Fix direction:** render text safely or use a properly sanitized Markdown renderer. Test raw HTML, event attributes, unsafe links, and ordinary Markdown. Address before Groq integration.

## P1 — Python optimization ignores the user's exposure limit and risk-free rate

**Evidence:** live request for AAPL, MSFT, NVDA, AMZN, GOOGL with `max_weight: 0.2`, `risk_free_rate: 0.02` returned HTTP 200, `engine: python-pytorch-slsqp`, `cached: false`, and 35% allocations to GOOGL and NVDA. Five assets make a 20% limit feasible, so this is not a two-stock feasibility issue.

**Location:** `app.py:189`, `:195`; `server/src/routes/optimize.routes.js`; `server/src/services/quant.service.js`.

Node forwards the settings, but Python hardcodes max weight 0.35 and risk-free rate 0.04. The UI offers saved preferences that cannot take effect on this engine. Separately, `optimizer.py:88` silently relaxes infeasible limits to 1 / number of assets.

**Fix direction:** validate and apply settings end to end; expose or reject infeasible settings rather than silently changing them. Verify both Python and fallback behavior.

## P1 — Failed portfolio saves are silently treated as local success

**Evidence:** browser-confirmed using authenticated profile fixtures and intercepted HTTP 500 responses for portfolio updates. Depositing a valid $600 changed local cash from $1,000 to $1,600 and closed the modal without an error. A one-share purchase likewise changed holdings/cash locally and closed the dialog while the save failed.

**Location:** `website/src/api.js:99`, `website/src/App.jsx:235`, `:263`, `:279`, `:289`; `Trading/TradeModal.jsx:85`.

`updateUserPortfolio` returns null on HTTP failure; callers neither await success nor display a failure. A future reload/account refresh can disagree with the visible ledger.

**Fix direction:** make save failures observable, define rollback or an explicit unsynced state, and prevent a success message until persistence is confirmed.

## P1 — Every deposit preset fails browser validation

**Evidence:** browser-confirmed: $5,000, $10,000, $25,000 and $50,000 are all invalid. Edge offers $9,600 or $10,100 as alternatives to $10,000. $100 and $600 pass.

**Location:** `website/src/components/MyPortfolio/MyPortfolio.jsx:403` and the input immediately after it.

The input combines `min="100"` with `step="500"`. Valid amounts are 100 + n * 500, so neither the default amount nor the presets can be submitted.

**Fix direction:** align the step/minimum with the intended monetary increments and test every preset plus a custom amount.

## P1 — Empty portfolios are replaced by demo holdings

**Evidence:** browser-confirmed: seeding `rf_portfolio_holdings_guest` with `[]` and reloading produces five portfolio rows. Code review also found the profile route populating empty holdings with demo assets.

**Location:** `website/src/data/marketSignals.js:144`, `website/src/App.jsx:49`, `server/src/routes/auth.routes.js` (`GET /me`).

The local loader accepts only nonempty arrays; App and the profile route also conflate empty holdings with an uninitialized account. Selling the last holding can therefore appear to undo itself after reload.

**Fix direction:** distinguish missing data from an intentionally empty portfolio, with explicit demo initialization.

## P1 — Reference prices and seeded recommendations are presented as live model output

**Evidence:** code-confirmed and visible in the browser. Portfolio quotes and daily returns are generated from reference prices and ticker hashes; the historical price chart is a separate real API path. AAPL's reference portfolio price was $234.80 while the previous live price-history check returned recent closes around $350.

**Location:** `website/src/data/marketSignals.js:4`, `:65`, `:218`; `MyPortfolio.jsx`; `OptimalSignals.jsx`.

The UI uses "LIVE", real-time valuation language, and model rationale/conviction scores although candidate scores, rationales, and default alphas are seeded. Some recommendation cards remain for stocks outside the optimized basket.

**Fix direction:** explicitly label demo/reference information, show data timestamps and provenance, and derive model recommendations from actual responses before calling them current model signals.

## P1 — Zero model allocations are treated as missing

**Evidence:** code-confirmed.

**Location:** `website/src/data/marketSignals.js:236`, `:239`, `:253`; `website/src/components/MyPortfolio/MyPortfolio.jsx:33`.

Truthy checks discard a legitimate zero weight or zero alpha. Signal cards can retain a default 20% allocation, and portfolio advice turns zero into null rather than an exit/rebalance signal. Very small nonzero floating-point weights do not trigger precisely the same branch; exact zero does.

**Fix direction:** use explicit presence/null checks and define how zero allocations affect buy candidates and holdings advice.

## P2 — Optimization success toast appears after failed requests

**Evidence:** browser-confirmed with an intercepted HTTP 500 response. The results section reported "Audit failure" while the toast said "Algorithmic Optimization Complete: Signals updated to latest market frontier!".

**Location:** `website/src/components/OptimalSignals/OptimalSignals.jsx:42`.

The toast runs on a 1.2-second timer, independent of the request result.

**Fix direction:** await completion and derive progress/success/failure from actual request state.

## P2 — Editing the selection leaves old results displayed

**Evidence:** browser-confirmed: optimize four stocks, deselect MSFT, and the selection says three while the result table still contains four rows, without an out-of-date indicator.

**Location:** `website/src/App.jsx:127`; `Results/Results.jsx`.

**Fix direction:** invalidate results on selection changes or retain the original calculation inputs and clearly mark stale results. Include selection changes during an in-flight request.

## P2 — Risk preferences display defaults after login

**Evidence:** browser-confirmed with a mocked login returning aggressive risk tolerance and a 20% exposure limit. Reopening account preferences displayed moderate and 35%. Restoring the same profile before the initial application render did display its settings correctly, so this specifically reproduces the login/account-change path.

**Location:** `website/src/components/UserAuth/AuthModal.jsx:11`.

Form state is initialized once and does not synchronize when the user changes. Saving without noticing can overwrite the actual preferences.

**Fix direction:** initialize the preference editor from the current profile when it opens or the account changes, while preserving edits during a save.

## P2 — Mobile trade dialog is clipped and overlapped

**Evidence:** browser-confirmed and visually inspected. At 390 x 667 the dialog runs from y = -94 to y = 761. Its overflow is hidden, and its fixed backdrop has no scrolling treatment. At 390 x 844 it still extends beyond the viewport. The navbar covers the top, and the floating copilot button overlaps the lower action area.

**Location:** `website/src/components/Trading/TradeModal.css:6`, `:21`; `AgentCopilot/AgentCopilot.css:1`; navbar styles in `App.css`.

**Fix direction:** constrain dialog height with internal scrolling, establish a modal layer above page chrome, and keep close/submit controls reachable at short heights.

## P2 — Mobile page overflows horizontally

**Evidence:** browser-confirmed. A fresh 390px page has 404px document width; with selection/results the audit observed 435px at 390px and 320px widths. Desktop/tablet checks at 1440, 1024 and 768 did not show document overflow in the tested state. The portfolio toolbar's nonwrapping controls are one contributor.

**Location:** `website/src/components/MyPortfolio/MyPortfolio.css:181`; selection dock and result layout in `App.css`.

**Fix direction:** let control groups wrap/shrink; retain horizontal scrolling inside wide table wrappers instead of making the document itself wider.

## P2 — Dialog and form keyboard/screen-reader support is incomplete

**Evidence:** browser and code-confirmed. Opening sign-in leaves focus on the underlying navbar button, Escape does not close it, and there is no dialog role/aria-modal or focus trap. Email/password inputs have visible labels but no label association. Trade/deposit dialogs have similar missing dialog semantics. Stock cards use aria-pressed on role=listitem, which does not expose toggle-button semantics.

**Location:** `UserAuth/AuthModal.jsx:182`, `:258`, `:270`, `:281`; `Trading/TradeModal.jsx:107`; `MyPortfolio.jsx` deposit markup; `StockSelector/StockCard.jsx`.

**Fix direction:** use accessible dialog behavior with focus entry/trapping/restoration, Escape handling, labelled controls, and valid stock selection semantics. Preserve existing Enter/Space selection behavior.

## P3 — Healthy startup is artificially delayed

**Evidence:** code-confirmed: `MIN_DISPLAY = 4000` holds the loading screen for at least four seconds even when the backend is already healthy. Backend-unavailable state waits up to five minutes for its explicit retry UI.

**Location:** `website/src/components/LoadingScreen.jsx:14`.

**Fix direction:** show the app when ready and provide useful retry/status feedback sooner when it is not.

## Working behaviors checked

Stock search returns AAPL alone for "aapl"; bulk selection stops at 35; Clear returns selection to zero. Optimization click/Enter/Space, selected/default signal baskets, loading disablement and API error display pass the existing regression suite. The previous live four-stock optimization returned fresh Python results and rendered four rows. This pass also confirmed a successful fresh five-stock Python API response while diagnosing constraint handling. Mobile navigation opens. Copilot styling and emoji removal were visually inspected on mobile.

## Limits

The issues above were reported, not fixed, except for emoji cleanup. Real authenticated Atlas writes, real trades, production hosting, model quality, and exhaustive assistive-technology testing were not performed. Synthetic account tests verify frontend behavior under controlled replies, not successful end-to-end account persistence. The existing keyword copilot and its backend metric/history limitations still require their own integration work. Docker/third-party service output is outside the application-owned logging cleanup.
